# Legacy Prediction Migration Map

Branch: `test-matrix-of-destiny-rhd` only  
Status: inventory and mapping design; legacy content has not yet been moved.

## Non-negotiable migration rules

1. Keep all calculation functions, arithmetic, input normalization, date/time handling, and result-code generation in the existing JavaScript engine.
2. Move only editable interpretation/content data into the JSON repository.
3. Preserve every legacy key and lookup path through an adapter. Do not rename categories, question IDs, feature keys, or result numbers during the first migration.
4. Keep original content as the source of truth until parity tests pass. No deletion of legacy constants during extraction.
5. Runtime content must be published before it can replace the matching legacy content. Missing JSON records must fall back to the existing JS data.
6. Never write to `main`, `Admin`, or Production as part of this work.

## Record identity convention

Use stable IDs that preserve legacy lookup identity, for example:

- `engine1:topic:work:result:1`
- `engine1:prediction:rabbit:1`
- `engine1:prediction:ascendant:aries`
- `engine1:rhd:habit:1`
- `engine2:deity:1`
- `engine3:question:<legacy-question-id>`
- `engine3:prediction:<category>:<result-number>`
- `engine4:tarot:major:1`
- `engine4:rune:fehu`
- `engine4:crystal:1`

The exact IDs must be confirmed against every legacy lookup before import. Do not create duplicate IDs or silently normalize legacy keys.

## Migration phases

### Phase 1 — Inventory and schema mapping
- Completed: identified the major authored data objects and their engine ownership.
- Next: inspect all nested keys, record counts, duplicate keys, cross-engine references and question IDs.
- Produce an extraction manifest with source object, legacy key, target collection, stable record ID and payload hash.

### Phase 2 — Non-destructive extraction
- Convert authored data objects into JSON records without changing source JS.
- Keep each record below the repository's 45 KB record limit.
- Verify Thai text, newlines, arrays, Unicode symbols and emoji survive round-trip.
- Commit only to this test branch.

### Phase 3 — Compatibility adapter
- Add a read-only adapter that overlays published JSON content onto legacy data structures.
- For every missing or unpublished record, use the original JS constant.
- Do not allow JSON to override calculation constants, numeric mappings, formulas or generated matrices.

### Phase 4 — Parity tests
- Capture baseline outputs from the unmodified legacy engine for representative inputs across all four engines.
- Run the same inputs with JSON overlay enabled.
- Compare calculation values, result IDs, question selection, card/rune selection and rendered interpretation fields.
- Require exact parity for all calculation outputs and expected text parity for every migrated record.

### Phase 5 — Admin activation
- Only after parity tests pass, enable edits/publishing for the migrated record types.
- Keep Read-Only Admin non-mutating.
- Keep rollback/history and a legacy fallback available.
